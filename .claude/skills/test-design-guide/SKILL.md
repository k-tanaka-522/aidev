## 0. 本規約が存在する理由

前身プロジェクトの実績（Phase 1.5、承認機能のE2Eが34件中29件パスと報告されたが、UIに
承認画面への動線が存在せず利用者は機能に到達できなかった事故）が示すとおり、
**カバレッジの分母を実装から取ると、実装が設計・要件を満たしていない場合に
検出できない**。v2はこの原則をゾーン型モデルの制約（要件定義書という文書の確定を
Zone3まで遅らせる）の中でどう維持するかが最大の論点である。

01文書4.4.5節はこれを「ハリボテに加え、契約モック・決定ログ・帳票/バッチ台帳を
左岸の代替として扱い、ID体系を粒度別に複線化する」ことで解決する。本規約はこの
6種ID体系を試験設計・実装の規約として明文化する。

## 1. 最上位の原則

**カバレッジの分母は要件・設計（本規約が定めるID体系）から取る。実装から取らない。**

実装を読んでテストを書くと、実装が設計を満たしていない場合に検出できない。実装の
参照は期待結果の確認ではなく、**設計との差分の発見**のために行う。

**合格率はカバレッジではない。** 「34件中29件パス」は「書いたテストが通った率」で
あり、書いていないテストを測れない。分母が無い数値を成果として報告してはならない
（MUST NOT）。

## 2. v2の6種ID体系と試験レベルの対応（10.1節、01文書4.4.5節・4.4.6節が正本）

前身プロジェクトは要件ID（`F-xxx`）・遷移ID（`BD-021 #n`）の二層だったが、v2は
ハリボテ駆動モデルの制約に対応するため6種に拡張する。

| ID | 粒度 | 採番タイミング・採番者 | 分母となる試験レベル |
|---|---|---|---|
| `SCR-{連番}` | 画面1枚 | ハリボテHTML記述時、`mockup-generate`が採番 | （分母にしない。機械抽出の単位） |
| `HB-{連番}` | 機能／E2Eシナリオ1本（複数画面をまたぐ） | 同期点A⇔B通過時、QAが採番 | **E2Eの分母** |
| `API-{連番}` | 外部公開APIエンドポイント1本 | レーンBでOpenAPI operationId確定時、App-Architectが採番 | **IT（結合テスト）の分母** |
| `NFR-{連番}` | 非機能要件1件 | Zone0決定ログの非機能エントリ確定時、Consultant/Infra-Architectが付与 | **ST（システムテスト、非機能検証）の分母** |
| `RPT-{連番}` | 帳票1様式 | 帳票ハリボテ確定時、機構が自動採番 | `HB-ID`の経路情報として保持（帳票を伴う業務シナリオのE2E経路） |
| `BAT-{連番}` | バッチジョブ1本 | 入出力仕様・サンプルデータ確定時、QAが採番 | 画面経由なら`HB-ID`の経路情報、画面非経由（夜間バッチ等）は**そのままバッチカバレッジの分母** |

`SCR-ID`は画面が実体として存在する証跡であり、単独ではカバレッジの分母にならない
（1画面が複数の業務フローに登場しうるため）。**判定観点ごとに分母となるIDが異なる**
点に注意する（01文書4.4.5節、02文書10.1.2節）。

## 3. テストレベルの責務分担

「何を検証し、何を検証しないか」を定める。担当者の割当とは別物である。

| レベル | 検証するもの | 検証しないもの | 環境 | 主なオラクル | 分母 |
|---|---|---|---|---|---|
| UT（単体） | 関数・コンポーネント単体の入出力、分岐、バリデーション | 画面間遷移、API疎通、認可の実体 | ローカル（モック） | 戻り値・描画結果 | 関数／コンポーネントの分岐（IDなし。Coderが実装と同時に作成、01文書4.5節） |
| IT（結合） | フロント↔API↔DBの契約、冪等性、認可判定 | ユーザー操作の順序、画面の見た目 | dev（実APIまたは契約モック） | HTTPステータス・DBレコード | `API-ID`（エンドポイント×ケース） |
| E2E（動線） | ロール別業務動線の完遂、画面遷移条件、ロールガード、証跡が残ること | 個別APIの全ケース、境界値 | dev（実認証基盤・実API） | 画面表示＋**業務結果** | `HB-ID`（経由する`SCR-ID`/`RPT-ID`を含む） |
| ST（システム） | 非機能（性能・セキュリティ・監査ログ）、設計と実装の差分 | — | dev | 実測値・ログ | `NFR-ID` |
| UAT（受入） | 利用者が業務として使えるか | — | dev（stg 作成後は stg） | ユーザー・発注者の合意 | 06-03（受入テスト結果報告書）の検収条件 |

**上位レベルは下位レベルの不足を補完しない（MUST NOT）。** 「単体が薄いのでE2Eで
補完する」という方針は禁止である。

**実施主体の独立性（01文書7.3節・7.6節）**: IT以上（E2Eを含む）のテストは実装者
（Coder）ではなくQAが書く。UT（単体）はCoderが実装と同時に作成する（前身プロジェクト
から変更なし）。`HB-ID`のdocblock記載主体はQAである（01文書4.4.5節手順6）。

## 4. E2Eテストの定義

**特定のロールの利用者が、ログイン画面から始めて、画面上の要素だけを操作して業務目的を
完遂できること**を実環境相当で確認するテストである。検証対象はコンポーネントでもAPIでも
なく「動線と業務結果」である。

- 起点: 常にログイン画面。**例外**: ログインしない一般利用者の動線（公開ページからの申込み等）は、試験用の公開ページのURLから始める
- 経路: ハリボテ（`prototypes/`）で確定した遷移のみ。リンク・ボタン・キー操作で発生させる
- 終点: 業務結果が確認できる状態（証跡が記録された／一覧から消えた／進捗が更新された）
- 1シナリオ = 遷移の連鎖1本 = `HB-ID` 1つ以上への対応

### 禁止事項（MUST NOT）

1. `page.goto()` の使用。例外はログイン処理内部の`/login`と、URL直打ちによるガードを
   明示的に検証するシナリオのみ（`-DIRECT`接尾辞で正常系と区別する）
2. `.catch(() => {})` によるアサーション・待機の握りつぶし
3. アサーションの無いテスト。未実装なら `test.skip` / `test.fixme` に理由を書く
4. `waitForTimeout` による固定待ち。自動待機系のアサーションAPIを使う
5. 実装内部の語彙をオラクルにすること。オラクルは画面上のテキスト・ロール・業務結果で書く

### 必須事項（MUST）

1. シナリオ冒頭で「ロール」と「ログイン後の着地画面」を確認するアサーションを置く
2. 各シナリオのdocblockに`HB-ID`と経由する`SCR-ID`（該当すれば`RPT-ID`）を記載する（10.1節）
3. **業務結果のアサーションを最低1つ置く。** 画面要素の存在で代替しない
4. テストデータの事前条件はシナリオ側がfixtureで保証・破棄する

## 5. docblock記載規約（10.1節・4.3節）

| ディレクトリ | 起点ID | docblockへの記載 |
|---|---|---|
| `tests/e2e/` | `HB-ID` | `HB-ID`と経由する`SCR-ID`/`RPT-ID`を記載する（MUST） |
| `tests/integration/` | `API-ID` | `API-ID`を記載する（MUST） |
| 非機能検証テスト | `NFR-ID` | `NFR-ID`を記載する（MUST） |

記載フォーマット（`.claude/lib/static-analysis.js` がこの書式だけを数える。`@hbId` 等の別書式は分子0になる）:

- `HB-ID: HB-0001` / `API-ID: API-0001` / `NFR-ID: NFR-0001` / `BAT-ID: BAT-0001` の形で書く
- **1行に1ID**。1本の流れで複数のHB-IDを束ねるときは、行を分けて全て列挙する（`HB-ID: HB-0011, HB-0012` と並べると2つ目以降は数えられない）

```ts
/**
 * HB-ID: HB-0011
 * HB-ID: HB-0012
 * HB-ID: HB-0013
 * 経由: SCR-0020, SCR-0021, SCR-0022
 * 一般利用者が公開ページから申し込み、確認URLで取り消せることを確認する。
 */
test('申込み〜取り消し', async ({ page }) => { /* ... */ });
```

## 8. 報告フォーマット

合格率のみの報告は禁止である（MUST NOT）。以下を必ず併記する。

- `HB-ID`カバレッジ: n/N（未カバーのIDを列挙）
- `API-ID`カバレッジ: n/N
- `NFR-ID`カバレッジ: n/N
- skip / fixme 件数とその理由
- 検出した欠陥（**実装の欠陥と試験設計自体の欠陥を分けて記載**）
- 検証できなかった項目とその理由
- 実行環境・配備物の版（対象コミット）。同定できなければ「同定できない」と書く

未カバー項目は`docs/00_プロジェクト管理・ガバナンス/00-12_リスク管理台帳.md`へdefer
登録する。登録しない未カバーはGateを通さない（MUST NOT）。

## 9. 語彙の統一

設計（決定ログ・契約モック）と実装で語彙が食い違う場合、試験設計の前に決着させる。
決着までは試験仕様に両語彙を併記する。語彙が切れたまま試験を書くと、「どの設計要求を
検証したテストか」を追跡できなくなる。

## カバレッジ判定の原則（再掲）

**カバレッジの分母は要件・設計（本規約が定めるID体系）から取る。実装から取らない。**
合格率のみの報告（例:「E2E 34件中29件パス」）はカバレッジとして受理しない。
`skip`/`fixme`/握りつぶしは分子に数えない（`gate-check`10.1.2節と整合）。


## 10. 変更の大きさと試験の段数

機能の完了条件は変更の大きさで変える。**大きさは coder の作業後に qa が変更差分を見て判定する**。
実装者（coder）には判定させない。迷ったら大きいほうに倒す。`gate-check` は申告された大きさと差分を照合し、小さく見積もっていれば NG とする。
**Guard・Review・判定はどの大きさでも省かない**（数行の IaC 変更であるセキュリティ是正を、軽微扱いで道の外に出さないため）。

| 大きさ | 目安 | 完了までの段 |
|---|---|---|
| 小 | 文言・見た目・並び順・コメントのみ。API の入出力、画面遷移、認可に触れない。既存の E2E が参照する文言を変えていない（grep で確かめる） | 実装＋UT → レビュー → dev 反映 → スモーク |
| 中 | 画面の流れ、API の入出力（必須項目・応答の形）、入力チェックが変わる | 小に加えて、qa が関係する IT/E2E を書き足し、回帰対象と合わせて dev で流す |
| 大 | 新機能。認可・テナント分離・決済・個人情報・同時実行にかかわる変更。共通部品の変更 | 実装＋UT → レビュー → qa の IT/E2E → dev 反映 → dev で試験（新規＋回帰） → 判定（gate-check／security-guard） |

判定結果と各段の状態（未着手／済／NG）・証拠（コミット、試験結果ファイル）は機能ごとに
`.claude-state/features/<機能名>.json` に残す。中断後は未完了の段から再開する。
`git status --porcelain` が空でない（未コミットの変更が残る）状態の試験結果は受理しない。

### 10.1 機能ごとの回帰

中・大では、新しく書いた試験だけでなく、変更が壊しうる既存の試験も流す。

- 回帰対象 = 変更差分が触ったファイル・API・画面を共有する既存の IT/E2E（01文書5.2節の「連動影響」と同じ考え方）
- 特定は `impact-analysis` の軽量モードを使う。台帳（00-02/00-03）から引けない分は、変更ファイルの import・呼び出し元から逆引きする
- 認可・テナント分離・同時実行・共通部品に触れた場合は、テナント分離の総当たりと同時実行の試験を必ず含める
- 回帰対象のテストIDと結果を `features/<機能名>.json` と `.claude-state/test-runs/` に残す
- 既存試験が落ちたら期待値を緩めない。実装の欠陥か試験の陳腐化かを切り分け、実装の欠陥なら 00-13 に起票する
- 小は回帰を個別に選ばず、dev 反映後のスモークで代える

## 11. 回す頻度

毎日の全件実行はしない。きっかけごとに回す。

| きっかけ | 回す試験 |
|---|---|
| 機能ごと | 10章の段数どおり（中・大は 10.1 の回帰対象を含む） |
| dev デプロイごと | スモーク（`npm run test:smoke` 等、3分以内が目標）。sre がデプロイ直後に流す |
| 節目（マイルストーン完了・GZ2 前） | IT・E2E・テナント分離総当たり・同時実行の全件 |
| ローンチ前に1回と大きな構成変更時 | 性能、障害（外部サービス異常・通知の重複・途中でのトークン失効等）、システム試験（バッチ・監査ログ・復元・監視アラーム・費用）、実利用者による UI/UX 確認 |
| 月1回 | 品質管理: 見逃した不具合を「本来どの段で拾うべきだったか」で集計し、レビュー観点・試験に反映する。依存ライブラリの脆弱性確認 |

ローンチ前に必須の範囲は Zone0〜1 で決定ログに定める（例: 全 API の IT、テナント分離総当たり、主要 E2E、スモーク）。それ以外の未カバーは 00-12 に先送り登録する。

## 12. 試験環境とデータ

- 実行先は dev（stg 作成後は stg）。prod は対象外。実行前に接続先のアカウント・環境を確認する（例: `aws sts get-caller-identity`）
- 試験の前に配備物の版（対象コミット）を同定する。SPA のフォールバックは存在しないアセットにも 200 を返すため、200 を実在の根拠にしない。API とフロントの片方だけが古い状態もありうる
- 固定の試験テナントとロール別アカウントを作り置きする。資格情報はシークレットストアに置き、コード・リポジトリに書かない
- 開通の試験だけ使い捨てのテナントを作り、掃除スクリプトで消す
- 試験で作るデータには実行ID（例 `E2E-20260930-1512`）を付け、試験の最後に消す。残骸は掃除スクリプトで消す
- 消せないデータ（WORM の監査証跡等）を書く試験は、実データの環境で流さない
- メール・決済などの外部サービスは、各サービスのサンドボックス／シミュレーターを使う
- **有料の外部 API（生成 AI 等）は呼ばない**。呼び出し関数を差し替え、実出力を元にした録画（正常・検査違反・途中切れ・拒否・上限到達等）を返す
  - 録画には作成時のプロンプト等の版を記録し、今のコードの版と食い違えば UT が落ちるようにする（撮り直し忘れの機械的な検出）
  - 実呼び出しの評価は、出力に影響しそうな変更（プロンプト・モデル・検査規則）と大きな節目の結合試験のときだけ、**正常系に限って**、ユーザーまたは PM の指示で上限額の範囲で回す。最初の失敗で止め、終了後に録画を更新する。不具合の切り分けに実呼び出しを重ねない
- 何度流しても同じ結果になるように作る（既存データに依存しない）

## 13. 実行コマンドと結果ファイル

後で CI に移せるよう、試験は npm 等のコマンドで流し、結果は JSON に残す。

| コマンド（例） | 中身 | 置き場 |
|---|---|---|
| `npm test` | UT（coder） | `tests/**`（下の3つを除く） |
| `npm run test:it` | IT（dev の API を叩く） | `tests/integration/` |
| `npm run test:e2e` | E2E（Playwright） | `tests/e2e/` |
| `npm run test:smoke` | スモーク | `tests/smoke/` |

- 共通部品（トークン取得、TOTP 算出、シークレット読み込み、試験データの作成・削除）は `tests/support/`
- 結果は `.claude-state/test-runs/<日時>-<種別>.json` に保存する。判定（gate-check）はこのファイルを読み、件数を自ら数える
- `tests/integration/`・`tests/e2e/`・`tests/smoke/` は qa だけが書ける（coder は書けない。hooks で強制）
- バックグラウンドで流すときは `< /dev/null` で標準入力を閉じる（閉じないとハングすることがある）

## 14. 実行方針（ツール選定とエージェントの実行コスト）

試験は書くだけでなく**繰り返し実行される**。実行のたびに時間と（エージェントが回す場合は）コンテキストを消費するため、ツールと実行設定も設計対象とする（niigata-aha-SaaS の規約から継承）。

### 14.1 ツールの担当範囲を設定で固定する

UT（例: vitest）と E2E（例: Playwright）の担当範囲を、各設定ファイルの `include`／`testMatch` で互いに拾わないよう固定する（vitest の既定 include は `*.spec.ts` を含むため、放置すると Playwright のファイルを jsdom で実行して必ず失敗する）。同名テストの重複配置も禁止する。

### 14.2 エージェントが実行する場合の原則

**コストはツールではなく「何をコンテキストへ返すか」で決まる。**

禁止する:

1. **ブラウザ操作系の MCP サーバの利用**（Playwright MCP 等）。操作ごとにページのスナップショットが返り、同じ確認をスクリプトで行う場合より桁で高くつく
2. `page.content()`・`innerHTML` の全文出力（SPA 1ページで数万トークンに達する）
3. スクリーンショットを既定で読むこと。`screenshot: 'only-on-failure'` を維持し、画像を見るのは「何が成り立てば OK か」を文字で書けないときだけ

推奨する:

1. **判定をスクリプト側に置き、真偽値と URL だけを出力する**（ページの大きさに関係なく出力が数行に収まる）
2. 確認したいことを先に列挙し、アサーションとして書いてから実行する。「とりあえず開いて眺める」は最も高くつく

### 14.3 既定の実行設定

- ブラウザは chromium のみ。クロスブラウザは環境変数で明示したときだけ
- レポーターは `list`。html レポートは明示したときだけ生成する
- 実行成果物（`playwright-report/`・`test-results/`・スクリーンショット）はリポジトリに含めない

### 14.4 動作確認と試験を混同しない

実装者が変更を確かめるための使い捨てスクリプトは**試験ではない**（分母 ID を持たず、トレーサビリティに載らない）。確認が済んだら消し、残す価値があるものは qa が本規約に従って `tests/` へ書き直す。
逆に、使い捨てスクリプトで見つけた不具合は必ず試験として定着させる。定着させない限り、同じ欠陥は次の変更で再発する。
