## 0. 本規約が存在する理由

annotationの実績（Phase 1.5、承認機能のE2Eが34件中29件パスと報告されたが、UIに
承認画面への動線が存在せず利用者は機能に到達できなかった事故）が示すとおり、
**カバレッジの分母を実装から取ると、実装が設計・要件を満たしていない場合に
検出できない**。v2はこの原則をゾーン型モデルの制約（要件定義書という文書の確定を
Zone3まで遅らせる）の中でどう維持するかが最大の論点である。

01文書4.4.5節はこれを「ハリボテに加え、契約モック・決定ログ・帳票/バッチ台帳を
左岸の代替として扱い、ID体系を粒度別に複線化する」ことで解決する。本規約はこの
6種ID体系を試験設計・実装の規約として明文化する。

## 1. 最上位の原則

**カバレッジの分母は要件・設計（本規約が定めるID体系）から取る。実装から取らない。**

実装を読んでテストを書くと、実装が設計を満たしていない場合に検出できない。実装の
参照は期待結果の確認ではなく、**設計との差分の発見**のために行う。

**合格率はカバレッジではない。** 「34件中29件パス」は「書いたテストが通った率」で
あり、書いていないテストを測れない。分母が無い数値を成果として報告してはならない
（MUST NOT）。

## 2. v2の6種ID体系と試験レベルの対応（10.1節、01文書4.4.5節・4.4.6節が正本）

annotationは要件ID（`F-xxx`）・遷移ID（`BD-021 #n`）の二層だったが、v2は
ハリボテ駆動モデルの制約に対応するため6種に拡張する。

| ID | 粒度 | 採番タイミング・採番者 | 分母となる試験レベル |
|---|---|---|---|
| `SCR-{連番}` | 画面1枚 | ハリボテHTML記述時、`mockup-generate`が採番 | （分母にしない。機械抽出の単位） |
| `HB-{連番}` | 機能／E2Eシナリオ1本（複数画面をまたぐ） | 同期点A⇔B通過時、QAが採番 | **E2Eの分母** |
| `API-{連番}` | 外部公開APIエンドポイント1本 | レーンBでOpenAPI operationId確定時、App-Architectが採番 | **IT（結合テスト）の分母** |
| `NFR-{連番}` | 非機能要件1件 | Zone0決定ログの非機能エントリ確定時、Consultant/Infra-Architectが付与 | **ST（システムテスト、非機能検証）の分母** |
| `RPT-{連番}` | 帳票1様式 | 帳票ハリボテ確定時、機構が自動採番 | `HB-ID`の経路情報として保持（帳票を伴う業務シナリオのE2E経路） |
| `BAT-{連番}` | バッチジョブ1本 | 入出力仕様・サンプルデータ確定時、QAが採番 | 画面経由なら`HB-ID`の経路情報、画面非経由（夜間バッチ等）は**そのままバッチカバレッジの分母** |

`SCR-ID`は画面が実体として存在する証跡であり、単独ではカバレッジの分母にならない
（1画面が複数の業務フローに登場しうるため）。**判定観点ごとに分母となるIDが異なる**
点に注意する（01文書4.4.5節、02文書10.1.2節）。

## 3. テストレベルの責務分担

「何を検証し、何を検証しないか」を定める。担当者の割当とは別物である。

| レベル | 検証するもの | 検証しないもの | 環境 | 主なオラクル | 分母 |
|---|---|---|---|---|---|
| UT（単体） | 関数・コンポーネント単体の入出力、分岐、バリデーション | 画面間遷移、API疎通、認可の実体 | ローカル（モック） | 戻り値・描画結果 | 関数／コンポーネントの分岐（IDなし。Coderが実装と同時に作成、01文書4.5節） |
| IT（結合） | フロント↔API↔DBの契約、冪等性、認可判定 | ユーザー操作の順序、画面の見た目 | dev（実APIまたは契約モック） | HTTPステータス・DBレコード | `API-ID`（エンドポイント×ケース） |
| E2E（動線） | ロール別業務動線の完遂、画面遷移条件、ロールガード、証跡が残ること | 個別APIの全ケース、境界値 | dev/lab（実認証基盤・実API） | 画面表示＋**業務結果** | `HB-ID`（経由する`SCR-ID`/`RPT-ID`を含む） |
| ST（システム） | 非機能（性能・セキュリティ・監査ログ）、設計と実装の差分 | — | lab | 実測値・ログ | `NFR-ID` |
| UAT（受入） | 利用者が業務として使えるか | — | lab | ユーザー・発注者の合意 | 06-03（受入テスト結果報告書）の検収条件 |

**上位レベルは下位レベルの不足を補完しない（MUST NOT）。** 「単体が薄いのでE2Eで
補完する」という方針は禁止である。

**実施主体の独立性（01文書7.3節・7.6節）**: IT以上（E2Eを含む）のテストは実装者
（Coder）ではなくQAが書く。UT（単体）はCoderが実装と同時に作成する（この点はannotation
から変更なし）。`HB-ID`のdocblock記載主体はQAである（01文書4.4.5節手順6）。

## 4. E2Eテストの定義（annotation原則を継承）

**特定のロールの利用者が、ログイン画面から始めて、画面上の要素だけを操作して業務目的を
完遂できること**を実環境相当で確認するテストである。検証対象はコンポーネントでもAPIでも
なく「動線と業務結果」である。

- 起点: 常にログイン画面
- 経路: ハリボテ（`prototypes/`）で確定した遷移のみ。リンク・ボタン・キー操作で発生させる
- 終点: 業務結果が確認できる状態（証跡が記録された／一覧から消えた／進捗が更新された）
- 1シナリオ = 遷移の連鎖1本 = `HB-ID` 1つ以上への対応

### 禁止事項（MUST NOT）

1. `page.goto()` の使用。例外はログイン処理内部の`/login`と、URL直打ちによるガードを
   明示的に検証するシナリオのみ（`-DIRECT`接尾辞で正常系と区別する）
2. `.catch(() => {})` によるアサーション・待機の握りつぶし
3. アサーションの無いテスト。未実装なら `test.skip` / `test.fixme` に理由を書く
4. `waitForTimeout` による固定待ち。自動待機系のアサーションAPIを使う
5. 実装内部の語彙をオラクルにすること。オラクルは画面上のテキスト・ロール・業務結果で書く

### 必須事項（MUST）

1. シナリオ冒頭で「ロール」と「ログイン後の着地画面」を確認するアサーションを置く
2. 各シナリオのdocblockに`HB-ID`と経由する`SCR-ID`（該当すれば`RPT-ID`）を記載する（10.1節）
3. **業務結果のアサーションを最低1つ置く。** 画面要素の存在で代替しない
4. テストデータの事前条件はシナリオ側がfixtureで保証・破棄する

## 5. docblock記載規約（10.1節・4.3節）

| ディレクトリ | 起点ID | docblockへの記載 |
|---|---|---|
| `tests/e2e/` | `HB-ID` | `HB-ID`と経由する`SCR-ID`/`RPT-ID`を記載する（MUST） |
| `tests/integration/` | `API-ID` | `API-ID`を記載する（MUST） |
| 非機能検証テスト | `NFR-ID` | `NFR-ID`を記載する（MUST） |

記載フォーマット例（TypeScript, Playwright想定）:

```ts
/**
 * @hbId HB-0001
 * @via SCR-0001, SCR-0002
 * 医師が画像をアップロードし、解析結果を確認できることを確認する。
 */
test('HB-0001: 画像アップロード〜解析結果確認', async ({ page }) => { /* ... */ });
```

## 6. トレーサビリティ

`HB-ID`×`SCR-ID`/`RPT-ID`/`BAT-ID`/`API-ID`のマトリクスは
`docs/00_プロジェクト管理・ガバナンス/00-02_HBトレーサビリティ台帳.md`
（`BAT-ID`は`00-03_バッチトレーサビリティ台帳.md`）に置き、これをZone3までの
暫定カバレッジ分母とする（03文書3.2.1節が列の正本）。Zone3で`traceability-reverse`
（QA担当）が正式要件ID（`F-{領域}-{連番}`等）へ変換し、`05-02`トレーサビリティ
マトリクス（正式版）を生成する（01文書4.4.5節）。

試験仕様を書く前に、対応する`HB-ID`/`API-ID`/`NFR-ID`が台帳・決定ログに存在することを
確認する（MUST）。存在しない試験は「なぜ実施するのか」を説明できないため書いてはならない
（MUST NOT）。

## 7. gate-checkの分母・分子（10.1.2節、再掲）

| ゾーン | 分母 | 分子 |
|---|---|---|
| Zone1〜2 | `HB-ID`全件＋`API-ID`全件＋`NFR-ID`全件＋画面非経由の`BAT-ID`全件 | E2Eは`tests/e2e/`docblockの`HB-ID`、ITは`tests/integration/`docblockの`API-ID`、STは非機能検証テストのdocblockの`NFR-ID` |
| Zone3以降 | Zone3で生成されたRTM（正式要件ID起点） | 同上（要件ID化後） |

`skip`/`fixme`/握りつぶしは分子に数えない（MUST NOT）。

## 8. 報告フォーマット

合格率のみの報告は禁止である（MUST NOT）。以下を必ず併記する。

- `HB-ID`カバレッジ: n/N（未カバーのIDを列挙）
- `API-ID`カバレッジ: n/N
- `NFR-ID`カバレッジ: n/N
- skip / fixme 件数とその理由
- 検出した欠陥（**実装の欠陥と試験設計自体の欠陥を分けて記載**）
- 検証できなかった項目とその理由

未カバー項目は`docs/00_プロジェクト管理・ガバナンス/00-12_リスク管理台帳.md`へdefer
登録する。登録しない未カバーはGateを通さない（MUST NOT）。

## 9. 語彙の統一

設計（決定ログ・契約モック）と実装で語彙が食い違う場合、試験設計の前に決着させる。
決着までは試験仕様に両語彙を併記する。語彙が切れたまま試験を書くと、「どの設計要求を
検証したテストか」を追跡できなくなる。

## カバレッジ判定の原則（再掲）

**カバレッジの分母は要件・設計（本規約が定めるID体系）から取る。実装から取らない。**
合格率のみの報告（例:「E2E 34件中29件パス」）はカバレッジとして受理しない。
`skip`/`fixme`/握りつぶしは分子に数えない（`gate-check`10.1.2節と整合）。
