# doc-style-guide（文書スタイル規約）

> 版数: M1実装（実装対象: docs/v2/02_実行基盤アーキテクチャ.md 9.2節・4.2節、
> docs/v2/03_成果物体系定義書.md 8章。`.claude/docs/40_standards/`の後継の一部）
> `user-invocable: false` は設計書5.1節が定める本来の値（自動参照Skillのため、
> ユーザーが明示的に呼ぶものではない）。`/home/user/annotation/.claude/skills/doc-style-guide/SKILL.md`
> を基礎とし、03文書8.4節・8.5節が定めるv2固有の追加要求（`生成区分`必須化、
> 決定ログからの引用節、drawio/Mermaid使い分け）を反映する。

## 責務

`docs/02〜07`配下の文書（01は独立ディレクトリを持たない、02文書4.2.1節）のヘッダー・
語調・構成規約を定める。`生成区分`必須フィールドを含む（値は03文書8.4節と統一）。

## 呼び出し元・連携先

- 呼び出し元: `docs/{02〜07}/.claude/skills/reverse-doc`・`traceability-reverse`（自動。
  M2でディレクトリスコープSkillが実装され次第、当該Skillのウォームアップ時に本Skillが
  自動参照される想定。具体的な発火条件はM2で確定する）

## 文書ヘッダー（v2版、必須フィールド追加。03文書8.4節）

すべての対象文書の冒頭に以下を記載する（MUST）。

生成区分: 実装反映(as-built) | 実装反映(as-built) - スナップショット版 | 事前設計(前倒し) | 手動作成
---
```

### `生成区分`フィールド（MUST、9.2節・03文書8.4節）

値は次の4つのいずれかとする（`doc-header-guard.js`、7.3節#4が機械チェックする対象と一致させる、MUST）。

| 値 | 用途 |
|---|---|
| `実装反映(as-built)` | Zone3の`reverse-doc`が実物・決定ログから生成した通常の文書 |
| `実装反映(as-built) - スナップショット版` | GZ2→GZ3で一度だけ全量生成するローンチスナップショット（03文書5.3.3節）。生成日時固定・以降の差分検査（5.4節の生成可能性検査）の対象外という特殊な意味を持つ |
| `事前設計(前倒し)` | 要件定義前倒しオプション（`requirements-first`）選択時、Zone1のうちに執筆する前倒し要件定義書（02文書8.7節） |
| `手動作成` | 上記のいずれにも該当しない手動作成文書（例外的） |

### 検査対象範囲（版1.4で確定、9.2節・7.3節#4）

検査対象は`docs/0[2-7]_**`に限定する。`docs/00`・決定ログ（`decisions/**`）・`docs/v2/*`
（本フレームワーク自身の設計書）は対象外とする。

|---|---|---|---|

```

## 語調・用語

- **である調**を使用する（です/ます調不可、MUST NOT）
- 初出略語は正式名称を併記する（MUST）
- MUST/SHOULD/MAY は RFC 2119 準拠で使い分ける

## セクション構成テンプレート（annotationの区分を継承、v2固有の追加あり）

### 設計書系（03番・04番）— **v2で「2.5 決定ログからの引用」を追加**（03文書8.4節）

```
1. はじめに（目的/適用範囲/関連文書/用語集）
2. 設計方針（基本方針/制約事項）
2.5 決定ログからの引用（当該設計に関わる決定ログID一覧と要旨） ← v2追加
3. 本文
4. 非機能要件への対応
5. AWS Well-Architected 対応（該当する場合）
6. 三省二ガイドライン対応（該当する場合）
7. 残課題
```

「2.5 決定ログからの引用」は、01文書4.7節の「決定と根拠は決定ログに残し、記述系文書は
リバースする」という線引きを、生成物の中で可視化するための節である。`reverse-doc`は
ここに該当決定ログのIDと要旨を**転記**する（新規生成しない、8.6節の「転記であり生成では
ない」原則を踏襲）。決定ログに存在しない判断は「未記載」と明記し、実装から推測して
後知恵の作文をしない（MUST NOT、8.6節・9.3節）。

### 計画書系（00番・05番の一部）

```
1. はじめに → 2. 計画概要 → 3. 本文 → 4. リスク → 5. 品質基準 → 6. 成果物一覧
```

### 結果報告書系

```
1. はじめに → 2. 実施概要 → 3. 結果 → 4. 分析 → 5. 残課題 → 6. 結論
```

### 手順書系（06番、07-10番）

```
1. はじめに → 2. 作業概要 → 3. 作業手順 → 4. 異常時対応 → 5. 連絡体制
```

07-10番の各手順書は、対応する`07-00_運用設計書.md`の該当セクションと1対1で対応させる
（04文書5章）。

### 規程・方針書系

```
1. 目的 → 2. 適用範囲 → 3. 用語 → 4. 基本方針 → 5. 体制と責任 → 6. 本文 → 7. 教育 → 8. 違反時対応 → 9. 見直し → 10. 関連法令・GL対応箇所
```

## 図表（03文書8.5節、Mermaid/drawio使い分け）

annotationの「グラフィカル図は`.drawio`形式で別紙として管理する」規約を、v2でも
維持する（MUST）。ただし**図種別ごとに形式を定める**（「全図をMermaid」「全図をdrawio」
という一律の原則化はしない、MUST NOT一律原則化）。

| 図種別 | 形式 | 主な対応文書 |
|---|---|---|
| システム構成図・AWS構成図 | **drawio** | 04-01 |
| ネットワーク構成図 | **drawio** | 04-02 |
| 業務フロー図・運用フロー図（スイムレーン付き） | **drawio** | 02-01、03-09、07-10 |
| シーケンス図 | **Mermaid** | 03/04詳細設計 |
| ER図・データモデル図 | **Mermaid** | 03-03 |
| 状態遷移図 | **Mermaid** | 03/04詳細設計 |
| 画面遷移図 | 既定はMermaid。契約上の清書要求がある案件はdrawioを追加 | 03-05 |

drawio別紙を要する図種別も、`reverse-doc`実行のたびに**第1段階としてMermaidスケルトン
（本文中に残す内部生成用の中間成果物）を先に確定**し、GZ3のローンチスナップショット
生成時に**第2段階**として`drawio-diagram` Skill（要検証、9.7節）がdrawio別紙を生成する
二段階方式を取る（03文書8.5.2節）。drawio別紙が生成できない状態でも、本文のMermaid版
だけで内容を把握できるフォールバックを常に確保する（MUST）。

- 図: 「図X-Y: タイトル」、表: 「表X-Y: タイトル」と付番し、本文中で必ず参照する（MUST）
- draw.io は AWS4 シェイプライブラリを使用し、`vidanov/aws-architecture-diagram-skill`の
  ルールに準拠する

## ファイル命名規則（03文書9章が正本、本節は要約）

### 採番規則（3種類）

| ケース | 採番方式 | 例 |
|---|---|---|
| ディレクトリ直下の単独文書 | `{大区分2桁}-{連番2桁}_{文書名}.md` | `00-04_運用項目一覧.md`、`03-01_アーキテクチャ概要.md` |
| サブディレクトリ（文書群）を作る単位 | `{大区分2桁}-{10刻み2桁}` | `07-10`（運用手順書群）、`07-20`（マニュアル群） |
| 群の中の個別文書 | `{大区分2桁}-{10刻み2桁}-{連番2桁}_{文書名}.md` | `07-10-01_{運用項目名}対応手順.md` |

3階層目の採番（群）が必要になるのは現時点では07番のみである（03文書9.1節）。

### ファイル種別ごとの拡張子

```
{項番}_{文書名}.md          # 原本
{項番}_{文書名}.html        # HTML版（doc-html-render Skillが生成、9.6節）
{項番}_{文書名}_別紙{N}.md  # 別紙
{項番}_{文書名}_別紙{N}.drawio  # グラフィカル図
```

### 本規約の対象外（別のID体系）

`DL-{4桁}`（決定ログ）、`03-D-{モジュールID}`/`04-D-{リソースID}`（オンデマンド生成の
詳細設計モジュール）、`SCR-ID`/`HB-ID`/`RPT-ID`/`BAT-ID`/`API-ID`/`NFR-ID`
（トレーサビリティ起点ID）、`GZ{0,2,3}-99`（ゲート記録）は本節の採番規則とは独立した
ID体系であり混同しない（MUST NOT混同、03文書9.1節）。

## reverse-doc経由の実行時マーカー（9.2節）

`reverse-doc` Skill経由で生成されたことを示す実行時マーカーを用いて、`reverse-doc`を
経由せず直接`docs/02〜07`に書き込まれたファイルを識別し警告する。**この識別方式は
更新漏れへの脆弱性を持つ**（M4で`reverse-doc`実装時に、マーカーの具体的な実装方式
とあわせて確定する）。
