# ux-review（ハリボテの使い勝手のレビュー）

> 由来: salon-booking-platform。観点・基準の正本は `.claude/skills/ui-style-guide/UIUX_STANDARD.md`「使い勝手の観点」節（本書は進め方の正本）。
> 記述系文書ではない。結果は `.claude-state/ux-review/` の作業記録で、ハリボテが変われば作り直す。

## 責務

designer が作ったハリボテを、使う人が目的を果たせるかの観点で見て、**根拠のある指摘だけ**を、仮の重大度つきで PM に返す。ハリボテは書き換えない（直すのは designer）。

汎用の LLM による「良くして」型のレビューは誤検出が多い（Baymard の検証で指摘の約8割が誤り、CHI 2024 の比較で適合率 0.6 程度）。そのため本スキルは、(1) 数えれば分かることを先に機械で数え、(2) 観点を分けて1つずつ見て、(3) 指摘ごとに事実と根拠を必須にし、(4) 別の fork が1件ずつ確かめ、(5) 重大度は人が確定する、という順に組んでいる。

## いつ・誰が呼ぶか

```
designer がハリボテを作る・直す（mockup-generate / mockup-update）
  → orchestrate → ux-review review <画面>            … (a)(b)(c)  下書き {日付}-{対象}.draft.md
  → （流れ・画面群がそろったら）ux-review consistency <画面…> … (d)  下書き {日付}-{対象}-consistency.draft.md
  → orchestrate → ux-review verify <下書き>          … (e)  別の fork。確定前の結果 {日付}-{対象}.md
  → PM／ユーザーが重大度を確定                         … (f)
      S4・S3 → designer が直す → review からやり直す（S4・S3 が残る間は sync-check に進まない）
      S2・S1 → PM が起票を決め pmo が 00-13 へ（Zone2 で直す）
      0（問題でない）→ rejected.md に理由を足す（次のレビューの入力）
  → sync-check
```

- `review` と `verify` は**必ず別の起動**にする（同じ fork で自分の指摘を検証しない）。PM（orchestrate）が2回呼ぶ。
- 01文書7.6節のハリボテのレビュー（app-architect・consultant＝仕様・業務の整合）とは別物で、置き換えない。
- dev の実画面での作業の流れの確認は qa（Playwright）の延長で、本スキルの対象外。対象は `prototypes/` の HTML だけ。

## 置き場所

| もの | 場所 | 書くのは |
|---|---|---|
| 機械検査の結果・スクショ | `.claude-state/ux-review/{日付}-{対象}/check*.json`・`shot*-{幅}.png`・`el-*.png`・`view-*.png` | `check.js`・`shot.js` |
| 指摘の下書き | `.claude-state/ux-review/{日付}-{対象}.draft.md` | review／consistency の回（`save-report.js`） |
| 検証済みの結果（重大度は仮） | `.claude-state/ux-review/{日付}-{対象}.md` | verify の回（`save-report.js`） |
| シナリオ | `.claude-state/ux-review/scenarios.md` | review の回が「案」で足す。PM／ユーザーが「確定」にする |
| 却下の台帳 | `.claude-state/ux-review/rejected.md` | verify の回（検証で却下）と PM（重大度 0 で確定）が追記 |

`{対象}` は1画面ならファイル名（`admin-settings`）、流れなら流れの名前（`signup-flow`）。`{日付}` は日本時間の YYYY-MM-DD。

## スクリプト（`prototypes/.claude/skills/ux-review/scripts/`）

Playwright は npx キャッシュの 1.63 と Chromium を使う（package.json に依存を足さない。初回だけ `npx -y playwright@1.63.0 --version`、Chromium が無ければ `npx -y playwright@1.63.0 install chromium`）。**どれも `< /dev/null` を付けて動かす**（付けないとハングすることがある）。

| スクリプト | 使い方 | 出すもの |
|---|---|---|
| `check.js` | `node …/check.js --file=prototypes/x.html [--query=role=staff] [--click=#btn] [--label=dialog-on] < /dev/null` | 390px と 1440px での、押せる範囲（24px 未満と 2.5.8 の例外の判定・44px 未満・390px での縦の位置）、危険な操作と隣の間隔、文字と入力欄の枠のコントラスト、入力欄の数・必須と任意の表示・ラベルの位置・type／inputmode／autocomplete、横のはみ出し（scrollWidth と clientWidth、はみ出す要素、内側の横スクロール）、全体のスクショ |
| `shot.js` | `node …/shot.js --file=… --selector="#x" [--width=390] [--click=…] < /dev/null` ／ `--viewport` | 要素1つのスクショと事実（HTML・位置と大きさ・文字の大きさと色・背景色・中の文字）／最初の画面のスクショと、そこに入っている見出し・押せるものの一覧 |
| `save-report.js` | `node …/save-report.js --out=2026-10-07-x.draft.md <<'UXR_EOF'` … `UXR_EOF`（`--append` で追記） | `.claude-state/ux-review/` の中の .md／.json だけに書く |

- `--query` はハリボテの確認用の状態を切り替える URL パラメータ（ハリボテ側で役割・プラン等の出し分けを持たせている場合）。役割・状態ごとに出し分けがある画面は、主な状態をそれぞれ測る
- `--click` は押してから測る・撮る（ダイアログ、次の段）。押せなかったものは結果に出る
- スクショはページの中身だけが写る（ブラウザの枠・OS の部品は写らない）。確認用バー（`[data-proto-bar]`・`[data-proto-only]`）と「確認用」と書いた操作は数えない（除外した件数は出る）

## 入力（どの回も最初に読む。MUST）

1. 対象の HTML（冒頭のコメントに SCR-ID・根拠の DL・「決めたこと」が書いてある）
2. `prototypes/SCREEN_ID_INDEX.md` の該当行
3. 関係する決定ログ: 対象の SCR-ID・ISS・画面名で `docs/00_プロジェクト管理・ガバナンス/decisions/` を Grep し、HTML の冒頭に挙がった DL は必ず読む
4. `.claude/skills/ui-style-guide/UIUX_STANDARD.md`「使い勝手の観点」節
5. `.claude-state/ux-review/rejected.md`（却下済みの指摘。同じものを出さない）
6. `.claude-state/ux-review/scenarios.md`（確定・案のシナリオ）
7. 同じ画面の過去の結果（`.claude-state/ux-review/*-{対象}.md`）があれば、その指摘が直ったかも見る

## 手順: review（(a)(b)(c)）

```
0. 入力を読む（上の1〜7）
1. 画面の分類を決める（下の「画面の分類」）。分類で観点の重みが決まる
2. (a) 機械検査: check.js を、既定の状態と主な状態（--query・--click）ごとに回す
   → 出た数値は「事実」。そのまま指摘にしない。下の「機械検査の読み方」で指摘の候補にする
3. シナリオを決める: scenarios.md の確定・案から対象の画面を通るものを選ぶ。無ければ下の「シナリオの作り方」で
   利用者ごとに3〜5本を作り、scenarios.md に「案」として足す（save-report.js --append）
4. (b) 認知的ウォークスルー: シナリオごとに、画面を順にたどる（shot.js --viewport・--click で各段を撮って見る）。
   1つの操作ごとに4つの問いに答え、「いいえ」の操作を指摘の候補にする
     問1 その操作をしようと思うか（目的からその操作を思いつくか）
     問2 正しい操作に気づくか（見える・押せそうに見える・言葉が合っている）
     問3 その操作で目的が果たせると分かるか（ラベルと目的が結び付くか）
     問4 進んだと分かるフィードバックがあるか（押したあと、何が起きたか分かるか）
5. (c) 観点ごとの評価: 観点 A〜M を、重みが ◎ のものから1つずつ、別々に見る。1つの観点を見ている間は
   ほかの観点の問題を拾わない（混ぜると見落としと誤検出が増える）。△ の観点は明らかな問題だけを見る
6. 候補を「誤検出を防ぐ決まり」で自分で一度ふるい、似た指摘をまとめ、良い点を書き、下書きを保存する
   → node …/save-report.js --out={日付}-{対象}.draft.md
7. 戻り値: 下書きのパス、仮の S4・S3 の件数と ID、決定ブロック
```

## 手順: consistency（(d)）

同じ利用者が使う画面をすべて渡して、画面をまたいでだけ見える問題を探す回。1画面の review では見ない。

```
1. 対象の画面群（例: 申込みの5段、設定画面すべて）を Read し、各画面で check.js（既に結果があれば再利用）と shot.js --viewport を撮る
2. 次を表にして食い違いを探す: 同じ操作の言葉（保存・登録・確定・送信…）、主ボタンの位置と色、戻る・やめるの位置、
   見出しの階層、日付・時刻・金額の書き方、空・エラー・完了の見せ方、確認ダイアログの出る条件、ナビの並びと名前
3. 食い違いのうち、利用者が迷う・誤操作するもの（観点 J）だけを指摘にする。見た目だけの差は S1 の候補にまとめる
4. 下書きを保存する → {日付}-{対象}-consistency.draft.md
```

## 手順: verify（(e)、指摘を出した回とは別の fork）

下書きの理由づけを信じない。指摘を1件ずつ、HTML とスクショで事実から確かめ直す（review-dispatch の「指摘の個別検証（file:line 再確認）」と同じ考え方）。

```
1. 下書きと、その入力（上の「入力」1〜7）を読む
2. 指摘ごとに:
   a. 場所: 要素の指定が対象の HTML に実在するか（Grep）。shot.js --selector で撮り、指定の要素が写るか
   b. 事実: 書かれた事実（大きさ・色・文言・位置・状態）が、撮った結果と shot.js の数値に合うか
   c. 原則: 挙げた原則がその事実に当てはまるか（観点の表の「見ること」と照らす）。好み・言い換えだけなら却下
   d. 既決: 関係する決定ログと矛盾しないか（矛盾すれば却下し、DL 番号を書く）
   e. 却下済み: rejected.md に同じものが無いか
   f. 取り違え: ブラウザの枠・OS の部品・確認用バー・ハリボテのダミー値（固定の日付・名前）を画面の問題にしていないか
   g. 重大度: 下の基準で付け直す（仮のまま）
   → 結果を「確認」「書き直して確認」「却下（理由）」のどれかにする
3. 却下したものは rejected.md に追記する（--append。区分は「検証で却下」）
4. 確定前の結果を保存する → {日付}-{対象}.md（却下したものも理由つきで末尾に残す）
5. 戻り値: 結果のパス、確認・却下の件数、仮の S4・S3 の ID、決定ブロック
```

## 画面の分類（観点の重みを決める）

| 分類 | 当てはまる画面 | 主に見るもの |
|---|---|---|
| 業務ユーザーのスマホ | 現場の担当者が日々使う画面。390px が主 | 片手で届くか・業務の頻度に沿った並び |
| 一般利用者の申込み | 申込み・予約の画面と公開ページ。390px が主 | フォームと、申込みが確定したことの分かりやすさ |
| PC の管理画面 | 運営・管理者・取引先が使う画面（一覧・登録・請求等）。1440px が主 | グルーピングと一覧での比較 |

分類は `UIUX_STANDARD.md`「使い勝手の観点」節と同じにする。案件で分類を変えたら両方を直す。

迷うときは、重いほうの重みで見て、どちらの分類で見たかを結果に書く。

## 観点 A〜M と重み

重み: ◎ 必須で深く見る ／ ○ 通常 ／ △ 明らかな問題だけ。並びは「業務ユーザーのスマホ／一般利用者の申込み／PC の管理画面」。

| 観点 | 重み | 見ること（事実の取り方） |
|---|---|---|
| A タスクの完遂 | ◎／◎／○ | シナリオの成功の条件まで行き着けるか。行き止まり・戻れない・必要な情報が無い（ウォークスルーの結果） |
| B 業務の頻度に沿った並び・段階的に見せる | ◎／○／◎ | 毎日使う操作が最初の画面にあり、まれな設定は奥にあるか。最初から全部を見せていないか（`shot.js --viewport` の一覧と、業務の頻度の決定ログ） |
| C 片手で届くか・押せる大きさ | ◎／◎／△ | 押せる範囲 44px 以上、2.5.8（24px）の違反なし、毎日の主な操作が画面の中ほど〜下にあるか、上の隅は大きいか、危険な操作が離れているか（`check.js` の under24・under44・zone・danger。Hoober: 片手持ちは49%、画面の中央が押しやすく上の隅が遠い） |
| D 視覚の階層と視線 | ◎／◎／○ | 最初に目に入る3つが、その画面の目的と主な操作か。見出しを拾い読みして中身が分かるか（F 型の読み方）。Z 型の配置は根拠が弱いので理由にしない（`shot.js --viewport`） |
| E グルーピング | ○／○／◎ | 関係するものが近く・同じ枠・同じ見た目でまとまり、関係しないものが離れているか（近接・枠・類似）。**スクショで確かめる。CSS の値だけで判断しない** |
| F フォーム | ○／◎／○ | 項目は最小限か、必須と任意が明示されているか、ラベルは上か、入力の型（type・inputmode・autocomplete）は合っているか、入力中・離れたときに検証するか、不要な会員登録をさせていないか（`check.js` の forms。Baymard: 入力欄の数は少ないほど完了率が高い、必須と任意は両方明示する） |
| G 状態とフィードバック | ◎／◎／○ | 読み込み中・空・エラー・完了の各状態があるか、押したあと何が起きたか分かるか（`--query`・`--click` で状態を出して撮る） |
| H エラー防止と取り消し | ◎／◎／◎ | 取り返しのつかない操作の前に確認があるか、取り消せるか、間違えにくい選択肢になっているか（Shneiderman の黄金律: エラーを防ぐ・取り消せるようにする） |
| I 利用者の言葉か | ◎／◎／○ | 専門用語・社内の言葉・英語の略語を使っていないか。UIUX_STANDARD.md「文言」節と、決定ログの用語の決まり |
| J 画面をまたぐ一貫性 | ○／○／◎ | consistency の回で見る。review の回では見ない |
| K 情報の密度・一覧での比較・一括操作 | △／△／◎ | 一覧で並べて比べられるか、並べ替え・絞り込み、複数をまとめて操作できるか |
| L 信頼と安心 | △／◎／△ | 一般利用者が申し込んでよいと思えるか（提供者の情報・料金・取消の決まりが見える、個人情報を何に使うか分かる、確定の画面と連絡の案内） |
| M 既存の規約 | ○／○／○ | `check.js` の結果（コントラスト 1.4.3・1.4.11、2.5.8、横のはみ出し）と UIUX_STANDARD.md の各節 |

## 機械検査の読み方

| check.js の結果 | 指摘の候補にするとき | 候補にしないとき |
|---|---|---|
| `under24`（例外なし） | 2.5.8 違反として M・C の候補 | `exception` が inline・spacing のもの |
| `under44` | 業務ユーザーのスマホ・一般利用者の申込みで、シナリオの中で使う操作・毎日の操作なら C の候補 | PC の管理画面（1440px）だけで使うもの、まれな操作で 2.5.8 は満たすもの（S1 にまとめる） |
| `zone: top` | 毎日の主な操作が 390px で上の 1/3 にあれば C の候補 | ナビ・戻る等、上にあるのが通例のもの |
| `danger.close` | 危険な操作が隣と 8px 未満なら H・C の候補 | 確認ダイアログの中の「やめる」と並ぶもの（確認が既に防いでいる。並びは J で見る） |
| `contrast.fails` | M の候補（1.4.3） | `manual` のもの（背景画像・無効状態）は目で見てから |
| `forms[].fields[].labelPosition` が placeholder-only・none | F の候補 | 検索欄など、目的が見て明らかで決定ログがあるもの |
| `typeIssue` | F の候補（スマホで違うキーボードが出る） | ラベルの言葉の誤検知（例: 「件数」の説明文） |
| `overflow.overflowing`・`offenders` | 390px なら M・C の候補 | `innerScrollers` は意図した横スクロール（ナビ・表）か目で確かめる |

## シナリオの作り方

- 形は「**誰が・どの状況で・何を達成したい・成功の条件**」。**手順は書かない**（手順を書くとウォークスルーが答え合わせになる）
- 利用者ごとに3〜5本。**まれだが致命的なものを必ず1本**入れる（例: 誤って OFF・削除・解約する、二重に申し込んだように見える、他のテナントの情報が見える）
- 状況には、片手・短い時間・作業の合間・電話を受けながら、などの制約を入れる
- 例:
  - 業務ユーザーが作業の合間に片手・30秒で、電話で受けた依頼を登録する。成功の条件: 登録できたと画面で分かる
  - 一般利用者が通勤中にスマホで、来週の枠に申し込む。成功の条件: 日時と内容を確かめて確定し、確定したと分かる
  - 管理者が PC で、担当の10件のうち未対応のものを見つけて連絡する。成功の条件: 該当を見落とさず一覧で特定できる
  - （まれだが致命的）業務ユーザーが設定を見ているとき、指で触れて意図せず受付を止めそうになる。成功の条件: 止まる前に気づいて戻れる
- scenarios.md の各シナリオに ID（`UXS-{利用者}-{連番}`、例: `UXS-STAFF-01`）、状態（案／確定）、通る画面（SCR-ID）を付ける

## 誤検出を防ぐ決まり（MUST）

1. 指摘ごとに **根拠の原則・場所（SCR-ID・ファイル・要素の指定・スクショの領域）・確かめられる事実** の3つを書く。1つでも欠けたら指摘にしない
2. **指摘「なし」を許す**。観点ごとに「問題なし」と書いてよい。件数を出すために指摘を作らない
3. スクショの**ブラウザの枠・OS の部品**（アドレスバー・スクロールバー・通知・キーボード）を画面の一部と取り違えない。スクリプトのスクショにはページの中身だけが写る。ハリボテの**確認用バー**と「確認用」の切り替え、固定のダミー値（日付・名前・件数）も画面の問題にしない
4. **既決の決定ログと矛盾する指摘は出さない**（verify では却下する）。決定そのものに使い勝手の問題があると考えるときは、指摘ではなく「PM への相談」の節に分けて書く
5. **過去に却下した指摘**（rejected.md）を入力に入れ、同じ指摘を出さない。事情が変わったと考えるときは、何が変わったかを書いて「PM への相談」に回す
6. **好みを押し付けない**: 「〜のほうが良い」「モダンでない」は指摘にしない。原則に照らして利用者が迷う・誤る・遅れる事実があるときだけ指摘にする
7. 似た指摘は1件にまとめる（同じ原因・同じ直し方なら場所を列挙する）
8. 自信がないものは確信度を「低」と書く。低のものは S3 以上にしない

## 指摘の書式

```markdown
### UXR-{連番}: {一言の要約}
- 対象: SCR-xxxx / prototypes/xxx.html / `#selector`（状態: ?role=owner、押した: #btn-open）/ スクショ: {日付}-{対象}/shot-390.png の (x, y, w, h)
- 利用者とタスク: {分類}・{UXS-ID とシナリオの一言}
- 事実: {撮った・測った・読んだ事実。数値と文言をそのまま}
- 違反する原則: {観点 A〜M}・{原則の名前と出典（UIUX_STANDARD.md の節、WCAG の番号、NN/g の原則等）}
- 影響: 頻度 {毎日／ときどき／まれ}・影響 {完遂できない／誤操作／迷う・遅れる／見た目}・持続性 {慣れても続く／一度覚えれば済む}
- 重大度（仮）: S{4〜0}
- 直し方の案: {designer への案。1〜2行。複数あれば並べる}
- 確信度: 高／中／低
- 検証の結果: （verify の回が書く）確認／書き直して確認／却下（理由）
```

## 重大度（仮。確定は PM かユーザー）

影響（完遂できない＞誤操作＞迷う・遅れる＞見た目）を軸に、頻度と持続性で1段上げ下げする（NN/g の重大度の考え方）。

| 重大度 | 基準 | 扱い |
|---|---|---|
| S4 致命 | 主要タスクが完遂できない／取り返しのつかない誤操作が起きうる／テナント分離・個人情報など、案件の最上位原則にかかわる | **止める**（ハリボテで直す。直るまで sync-check に進まない） |
| S3 重大 | 多くの人が迷う／毎日の操作が片手で届かない／申込みが確定したか分からない | **止める**（ユーザーが受け入れると明示すれば例外。その記録を結果に残す） |
| S2 軽微 | 迷うが自力で抜けられる、まれな操作で起きる | 起票して Zone2 で直す |
| S1 見た目 | 使い勝手にはほぼ響かない見た目・揃え | まとめて直す |
| 0 問題でない | 検討したが問題でない | 却下し、理由を rejected.md に記録する |

## 結果ファイルの形

```markdown
# UX レビュー: {対象}（{日付}）
- 回: review／consistency／verify（下書き: {パス}）
- 対象: SCR-xxxx（prototypes/xxx.html、最終更新 {git log -1 --format=%h の値}）
- 分類と重み: 業務ユーザーのスマホ（◎ A B C D G H I）
- 見た状態: 既定／?role=owner＋#btn-open …
- 重大度はすべて仮。確定は PM かユーザー
## 要約
- 止める候補（仮 S4・S3）: UXR-01、UXR-03（なければ「なし」）
- 件数: S4 n／S3 n／S2 n／S1 n、却下 n
## 良い点
## シナリオとウォークスルー（UXS-ID ごとに、操作 × 4つの問いの表）
## 指摘（重大度の高い順）
## 機械検査の要約（check.js の要約をそのまま。どれを指摘にしたか）
## PM への相談（既決にかかわるもの・事情が変わったもの。なければ「なし」）
## 却下したもの（verify の回。理由つき）
```

rejected.md の1件の形: `- {日付} {対象} UXR-xx「{要約}」— 却下（{検証で却下／PM 確定／ユーザー確定}）: {理由。DL 番号があれば}`

## 戻り値（orchestrate へ）

結果ファイルのパス、止める候補（仮 S4・S3）の ID と一言、件数、PM への相談の有無。最後に委譲プロンプトが指定する形式の決定ブロック（ux-reviewer は判断しないので通常は「決定なし」）。
