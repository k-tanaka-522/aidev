## 1. この手順書は何か

このリポジトリ（aiDevフレームワーク自体の開発環境）は、現在 **v1（企画→要件定義→設計→実装→テスト→納品のフェーズ順次型）** のPM・エージェント定義で動いている。`docs/v2/01_プロセス定義書.md`・`02_実行基盤アーキテクチャ.md`・`03_成果物体系定義書.md`・`04_運用設計体系定義書.md` で設計した **v2（Zone/レーン型、ハリボテ駆動＋ローンチ時リバース）** の実装（M0〜M6）は既に完了しており、`.claude/v2-staging/` 配下に配置済みである。

**カットオーバー**とは、この `.claude/v2-staging/` 配下のv2完全版を `.claude/` 直下（実際にセッションを制御する場所）へ昇格させ、このリポジトリの開発モード自体をv1からv2へ切り替える、**一度きりの作業**を指す。

対象は「aiDevというフレームワーク自体の開発」であり、aiDevを使って別のプロダクトを新規開発する場合（`scripts/init-new-project.sh` でクローンした先のプロジェクト）には関係しない。そちらは最初からv2の状態で配布される。

## 2. なぜ手動実行なのか

`scripts/cutover-v2.sh` は用意済みであり、`--dry-run` での内容確認も済んでいる。しかし、このスクリプトを実行すると、**いま動いているセッション自身を制御しているファイル**（権限定義 `.claude/settings.json`、PMの役割定義 `.claude/CLAUDE.md`、委譲先サブエージェントの定義 `.claude/agents/*`）がその場で入れ替わる。

これをAIエージェント自身に実行させようとしたところ、自動モードの安全機構（実行内容を分類する分類器）が「自己改変」に該当すると判定し、実行を拒否した。実行者の権限を実行者自身が書き換えるという操作は、通常の「ファイルを編集する」作業とは性質が異なり、安全側に倒して拒否される設計になっている。この判定は、影響を切り離すために用意した隔離環境（git worktreeでの実行）でも同様に働き、回避できなかった。

したがって、本フレームワークは**この切替をAIエージェントには行わせず、必ず利用者（人間）が手動で実行する**という前提で設計されている。これは設計上の制約ではなく、意図した安全策である。

## 3. 実行前の準備（前提条件）

- **git の作業ツリーがclean であること**（未コミットの変更が無いこと）。スクリプトはこれを自動チェックし、cleanでなければ中断する。事前に `git status` を確認し、必要なら先にコミットしておくこと
- `.claude/v2-staging/CLAUDE.md`・`.claude/v2-staging/settings.json`・`.claude/v2-staging/agents/{consultant,app-architect,infra-architect,designer,coder,qa,sre}.md` が揃っていること（スクリプトが自動チェックする）
- `.claude/hooks/` に登録予定の hook 実体（`role-boundary-guard.js` 等10種）が揃っていること（スクリプトが自動チェックする）

これらはすべて `scripts/cutover-v2.sh` 自身が起動直後にチェックし、不足があればその場で中断する（実行前に利用者が個別にファイルの有無を調べる必要はない）。

## 4. 実行手順

### 4.1 dry-run で内容を確認する

```bash
bash scripts/cutover-v2.sh --dry-run
```

何が変更されるか（削除されるファイル・上書きされるファイル・作成されるバックアップ）の一覧が表示されるだけで、**実際には何も変更されない**。内容に見覚えのない変更が含まれていないか目視で確認すること。

### 4.2 実行する

内容に問題がなければ、本実行する。

```bash
bash scripts/cutover-v2.sh
```

このスクリプトが行う変更は次の4点のみである。

1. `.claude/agents/<name>/AGENT.md`（v1、ディレクトリ形式）を削除し、`.claude/v2-staging/agents/<name>.md` を `.claude/agents/<name>.md`（v2、フラット形式）としてコピーする（7エージェント分）。あわせて、削除対象のv1 `AGENT.md` 群からのみ参照されていた `.claude/agents/ORCHESTRATION_DESIGN.md` も削除する
2. `.claude/settings.json` を `.claude/settings.json.pre-v2-cutover.bak` としてバックアップした上で、`.claude/v2-staging/settings.json`（permissions全体＋hook全10種の完全版）で全面差し替える
3. `.claude/CLAUDE.md` を `.claude/CLAUDE.md.pre-v2-cutover.bak` としてバックアップした上で、`.claude/v2-staging/CLAUDE.md`（v2軽量版）で全面差し替える
4. v1専用の `prevent-pm-layer-violation.sh` hookを `.claude/settings.local.json` の登録から除去し、hook本体ファイルを削除する（v2では同等の役割を `role-boundary-guard.js` が担うため）

このスクリプトは **`git add`・`git commit` は行わない**。作業ツリーの変更のみで止まる。コミットは利用者（またはPM）が内容を確認した上で行うこと。

### 4.3 実行後、Claude Code のセッションを起動し直す

**実行後は、Claude Code のセッションを一度終了し、起動し直すこと。**

理由と検証状況を正直に記す。M3の実機検証では、hookの登録内容（`settings.json` の変更）は**セッションを再起動しなくても同一セッション内で反映される**ことを、実際にサブエージェントを起動してhookが発火する様子を確認して検証済みである。

しかし、これは `settings.json` の hook 登録についての検証結果に過ぎない。**`CLAUDE.md`（PMの主体定義）と `.claude/agents/*`（サブエージェント定義）の差し替えが、再起動なしで同一セッション中に反映されるかどうかは検証していない。** これらはセッション開始時に読み込まれるプロジェクトメモリ・エージェント定義である可能性があり、実行中のセッションが古い内容を保持し続けるおそれがある。確実を期すため、本手順書は再起動を必須の手順として案内する。

## 5. 切替後に確認すること

再起動後、次を確認すること。M3で実際に切替関連の不具合が発生した箇所を優先的に挙げる。

- **`.claude/agents/` がフラット7ファイルになっているか**（`.claude/agents/coder.md` のように直下にファイルがあるか。`.claude/agents/coder/AGENT.md` のようなv1ディレクトリ形式が残っていないか）
- **`.claude/CLAUDE.md` がv2版になっているか**（「ゾーン」「レーン」「Zone 0」等の語が含まれているか。v1の「フェーズ」「Phase 1〜6」という表現が残っていないか）
- **`.claude/settings.json` の hook 登録で、`command` が `node ` 前置になっているか**（例: `"command": "node .claude/hooks/role-boundary-guard.js"`）。M3の実機検証で、`node` を前置せず `.claude/hooks/xxx.js` とだけ登録すると、実行権限（`+x`）が付与されていない限り `Permission denied` で**無音のまま**hookが一切発火しない不具合が実際に発生した。`.claude/v2-staging/settings.json` はこの教訓を反映済みだが、切替後に改めて目視確認すること
- **`Agent` を対象とするhookのmatcherが `Task|Agent` になっているか**（M3の実機観測で、サブエージェント委譲時の実際のツール名は `Task` ではなく `Agent` であることが判明したため）
- 最初の数回のツール呼び出し（ファイル編集・サブエージェント委譲）を慎重に確認する。`role-boundary-guard.js` が意図せずPM自身の正当な書き込み（`docs/00_プロジェクト管理・ガバナンス/` 等）までブロックしていないか
- 残存しているはずのv1資産（`.claude/docs/10_facilitation/`・`.claude/docs/40_standards/`・`.claude/helpers/`・`.claude/commands/check.md`・`check-code.md` 等）が本当に削除済みか。これらの削除はM6のCoderタスクで実施済みのはずだが、本スクリプト自体はこの削除を行わないため、切替後に改めて `git status` 等で確認することが望ましい

問題が無ければ、変更を `git add`・`git commit` する（このコミット操作自体はスクリプトの範囲外であり、利用者またはPMが行う）。

## 6. 戻し方（ロールバック）

本スクリプトは作業ツリーの変更のみを行い、コミットはしない。想定外のブロックが多発する等、問題が起きた場合は次の手順で戻す。

```bash
git status                    # 何が変更されたか確認する
git diff --stat               # 変更ファイル一覧

git checkout -- .claude/CLAUDE.md .claude/settings.json .claude/settings.local.json
git checkout -- .claude/agents/    # 削除されたv1 AGENT.mdを復元する
```

**注意**: 本スクリプトは `.claude/agents/<name>/AGENT.md` を削除し、新たに `.claude/agents/<name>.md` を作成する。`git checkout -- .claude/agents/` だけでは、削除されたv1ファイルは復元されるが、新規作成されたv2の `.claude/agents/<name>.md` は「追跡外ファイル」として残ってしまう。完全に戻す場合は `git clean -fd .claude/agents/` も検討すること。ただし `git clean` は追跡外ファイルを問答無用で削除するため、**実行前に必ず `git status` または `git clean -n -d` で削除対象を確認すること**。

v1専用hookを戻す場合は次のコマンドを使う。

```bash
git checkout -- .claude/hooks/prevent-pm-layer-violation.sh
```

なお、切替時に作成される `.claude/settings.json.pre-v2-cutover.bak`・`.claude/CLAUDE.md.pre-v2-cutover.bak` は、`git checkout` を使わずに内容を見比べたいだけの場合の参考用として残る（gitの復元機能を使う場合は不要）。

`.claude/v2-staging/` 配下は本スクリプトが変更・削除しないため、再切替が必要になった場合も、常にこのディレクトリを起点に再実行できる。

## 7. 切替後に何が変わるか

- **プロセスモデル**: フェーズ順次型（企画→要件定義→設計→実装→テスト→納品）から、ゾーン/レーン型（Zone 0: 不可逆決定 → Zone 1: 探索・収束ループ〔レーンA/B/C並行〕 → Zone 2: 実装・硬化 → Zone 3: ローンチ時リバース → Zone 4: Mode B〕へ変わる。詳細は `docs/v2/01_プロセス定義書.md` 3〜4章
- **ロール境界の強制方法**: v1はCLAUDE.md上の文章で「PMはsrc/を書かない」等を言い聞かせる方式だったが、v2は `settings.json` のpermissionsと `role-boundary-guard.js` 等のhooksが機構的に強制する。文章での自己抑制には依存しなくなる
- **PMの主体定義の分量**: v1の `.claude/CLAUDE.md`（338行）から、v2版（150〜180行目安）へ大幅に縮小する。フェーズマップ・ゲート詳細・クロスレビュー詳細等は `orchestrate` Skillと `settings.json` 側へ移す
- **技術標準の参照方法**: v1はPMが `.claude/docs/40_standards/` を都度参照する構成だったが、v2ではサブエージェントが対象ディレクトリ（`src/**`・`infra/**`・`prototypes/**`等）を読み書きした時点で自動参照される `.claude/skills/code-style-guide/` 等に置き換わる
- **状態管理ファイル**: `.claude-state/project-state.json`・`tasks.json`・`decisions.json`（v1）から、`.claude-state/current-zone.json`・`process-option.json`・`decision-warnings.json`・`zone-gate-retry.json` 等（v2）へ変わる。v1状態ファイルからの自動マイグレーションは提供しない
- **カスタムコマンド**: `/check`・`/check-code` は廃止され、`gate-check` Skillへ機能が移管されている。`/init`・`/status`・`/next` は存続するが、内容はv2の語彙・機構に合わせて書き換え済みである（`.claude/commands/*.md`）

## 8. 既知の制約

`docs/v2/02_実行基盤アーキテクチャ.md` 14.3節が定めるとおり、**v2は新規案件立ち上げ時のみ選択可能なプロセスモデルであり、v1で進行中の案件をv2のプロセスモデルへ移行する経路は提供しない。** フェーズ順次型からゾーン/レーン型への転換は、単純なフォーマット変換では済まないためである。

本手順書が扱う「カットオーバー」は、あくまで**aiDevというフレームワーク自身の開発環境（このリポジトリ）の制御方式をv1からv2へ切り替える**ものであり、v1のプロセスモデルで既に進行中の別プロダクト案件をv2へ引き継ぐ手段ではない。そのような案件は、当該プロジェクトのブランチ・コミット上でv1のまま継続すること。
